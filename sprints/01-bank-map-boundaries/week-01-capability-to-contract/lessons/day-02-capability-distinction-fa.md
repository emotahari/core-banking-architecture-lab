# Day 02 — Capability در برابر Process، Business Service و System

- Day budget: 45 minutes — 22 lesson + 18 exercise + 5 exit ticket
- Output: Distinction Matrix برای ۱۵ مثال بانکی
- Banking case: افتتاح سپرده، اعطای تسهیلات، انتقال وجه و مسدودی قضایی

## 1. هدف قابل سنجش

در پایان باید بتوانی:

1. Business Capability را بدون استفاده از نام سامانه یا فناوری تعریف کنی.
2. Capability را از Process، Value Stream، Business Service، Product، System، Organization Unit و API جدا کنی.
3. یک عبارت مبهم بانکی را با آزمون‌های مشخص طبقه‌بندی کنی.
4. برای هر Capability، Outcome، Owner و KPI اولیه پیشنهاد بدهی.
5. تشخیص بدهی چه زمانی یک نام ظاهراً دامینی هنوز فقط نام Legacy Application است.

## 2. مسئلهٔ واقعی

در نقشه‌های سازمانی معمولاً فهرستی مانند زیر می‌بینیم:

- سامانهٔ تسهیلات
- ادارهٔ چک
- سرویس افتتاح حساب
- API استعلام مانده
- فرایند انتقال وجه
- محصول سپردهٔ کوتاه‌مدت

اگر همهٔ این موارد را در یک سطح از Diagram بگذاریم، Map از همان ابتدا چند نوع چیز متفاوت را مخلوط کرده است. نتیجه این می‌شود که تیم‌ها از روی نام‌های موجود Service می‌سازند، مالکیت تصمیم مبهم می‌ماند و تغییر یک Capability به چند سامانهٔ بدون مرز پخش می‌شود.

## 3. تعریف عملیاتی Business Capability

Business Capability بیان می‌کند **سازمان چه توانایی نسبتاً پایداری باید داشته باشد تا Outcome کسب‌وکاری تولید کند**؛ مستقل از اینکه امروز این توانایی با کدام فرایند، تیم، نرم‌افزار، Vendor یا فناوری اجرا می‌شود.

نمونه‌های مناسب:

- مدیریت رابطه با مشتری
- نگهداری وجوه مشتری
- مدیریت تعهدات اعتباری
- اجرای پرداخت و انتقال وجه
- اعمال محدودیت و مسدودی روی وجوه
- ثبت و گزارش آثار مالی

نمونه‌های نامناسب:

- `LoanSystem`؛ نام راه‌حل یا Application است.
- «بررسی درخواست در سه مرحله»؛ Process است.
- `POST /loans`؛ Contract فنی است.
- «ادارهٔ اعتبارات»؛ واحد سازمانی است.
- «وام مرابحهٔ فرهنگیان»؛ Product/Offering است.

Capability پاسخ `what` سازمانی است، نه `how` اجرایی.

## 4. هفت مفهوم مجاور

### 4.1 Process

Process توالی فعالیت‌ها، تصمیم‌ها و Hand-offها برای رسیدن به نتیجه است. Process تغییرپذیرتر از Capability است.

```text
Capability: مدیریت سپرده
Process: دریافت درخواست → احراز هویت → کنترل محصول → افتتاح → ابلاغ نتیجه
```

با حذف امضای کاغذی و افزودن Video KYC، Process تغییر می‌کند؛ Capability افتتاح و نگهداری رابطهٔ سپرده باقی می‌ماند.

### 4.2 Value Stream

Value Stream جریان ایجاد ارزش برای ذی‌نفع از Trigger تا Outcome است و می‌تواند چند Capability و چند Process را درگیر کند. «از درخواست تسهیلات تا دریافت وجه» یک Value Stream است، نه یک Capability منفرد.

### 4.3 Business Service

Business Service نمای قابل‌مصرف یک یا چند Capability برای مشتری یا شریک است. «خدمت انتقال آنی وجه» چیزی است که مصرف‌کننده دریافت می‌کند؛ پشت آن Capabilityهای ثبت دستور پرداخت، کنترل ریسک، جابه‌جایی وجه، تسویه و رسیدگی به مغایرت قرار دارند.

Business Service با `REST service` یا Microservice یکی نیست.

### 4.4 Product/Offering

Product بسته‌ای از ویژگی، قیمت، شرایط و تعهد قابل‌عرضه به بازار است. «سپردهٔ بلندمدت یک‌ساله» محصول است. Capability «طراحی و مدیریت محصول» یا «نگهداری سپرده» است.

### 4.5 Organization Unit/Team

واحد سازمانی پاسخ می‌دهد چه کسانی مسئول کارند. Capability پاسخ می‌دهد سازمان چه توانایی‌ای لازم دارد. یک تیم ممکن است چند Capability را پوشش دهد و یک Capability ممکن است میان چند واحد پراکنده باشد؛ این پراکندگی خود یک Risk برای Ownership است.

### 4.6 Application/System

System پیاده‌سازی فعلی بخشی از توانمندی‌هاست. «سامانه سپرده» ممکن است افتتاح، مانده، سود، Hold و گزارش را یکجا انجام دهد. این واقعیت Legacy نه اثبات می‌کند همهٔ آن‌ها یک Capability هستند و نه اثبات می‌کند باید یک Bounded Context بمانند.

### 4.7 API/Event

API و Event قرارداد تعامل‌اند. `GET /accounts/{id}/balance` یک Query Contract است؛ `FundsHeld` یک Fact منتشرشده است. هیچ‌کدام به‌تنهایی Capability نیستند.

## 5. جدول تشخیص سریع

| نوع | پرسش تشخیصی | نسبت پایداری | مثال بانکی |
|---|---|---|---|
| Capability | بانک باید چه کاری بتواند انجام دهد؟ | زیاد | مدیریت تعهدات اعتباری |
| Value Stream | ارزش از چه Trigger تا چه Outcome ایجاد می‌شود؟ | متوسط | از درخواست وام تا دریافت وجه |
| Process | کار با چه توالی انجام می‌شود؟ | متوسط/کم | فرایند افتتاح سپرده |
| Business Service | چه خدمتی به مصرف‌کننده عرضه می‌شود؟ | متوسط | انتقال آنی وجه |
| Product | چه بستهٔ شرایطی عرضه می‌شود؟ | متوسط | سپردهٔ یک‌ساله |
| Org Unit | چه گروهی پاسخ‌گوست؟ | کم/متوسط | ادارهٔ اعتبارات |
| System | اکنون با چه راه‌حلی اجرا می‌شود؟ | کم | سامانهٔ تسهیلات |
| API/Event | تعامل با چه Contractی انجام می‌شود؟ | کم | `LoanDisbursed` |

## 6. آزمون شش‌گانهٔ Capability

برای هر نام پیشنهادی شش سؤال بپرس:

1. آیا Outcome کسب‌وکاری قابل تعریف دارد؟
2. آیا بدون اشاره به فناوری یا نرم‌افزار قابل بیان است؟
3. آیا با تغییر Process هنوز باقی می‌ماند؟
4. آیا Business Owner قابل تعیین دارد؟
5. آیا KPI یا سطح بلوغ برای آن قابل سنجش است؟
6. آیا نام آن «توانایی» را می‌رساند، نه یک شیء، کانال یا واحد؟

اگر پاسخ چند سؤال منفی است، مورد احتمالاً Capability نیست یا نام‌گذاری آن ضعیف است.

## 7. پانزده مثال طبقه‌بندی‌شده

| عبارت | نوع غالب | دلیل کوتاه |
|---|---|---|
| مدیریت هویت و رابطهٔ مشتری | Capability | توانایی پایدار و Outcome محور |
| افتتاح حساب غیرحضوری | Business Service/Process | خدمت قابل‌عرضه با جریان اجرایی مشخص |
| سپردهٔ قرض‌الحسنه جاری | Product | بستهٔ شرایط و تعهد |
| سامانهٔ سپرده | System | راه‌حل نرم‌افزاری موجود |
| محاسبهٔ سود روزشمار | Domain Rule/Process step | قاعده یا فعالیت در Capability بزرگ‌تر |
| نگهداری وجوه مشتری | Capability | توانایی بنیادی بانک |
| ادارهٔ شعب | Organization Unit | ساختار پاسخ‌گویی |
| خدمت مسدودی قضایی | Business Service | نمای خدمت برای مرجع/عملیات |
| اعمال Hold روی ماندهٔ قابل برداشت | Use Case | قصد مشخص در یک Context |
| `POST /holds` | API Operation | Contract فنی |
| `FundsHeld` | Event | Fact رخ‌داده |
| از درخواست وام تا واریز | Value Stream | جریان End-to-end ارزش |
| ارزیابی اهلیت اعتباری | Capability | توانایی تصمیم‌گیری اعتباری |
| کمیتهٔ اعتباری | Organization/Decision mechanism | سازوکار تصمیم فعلی |
| Core Banking | Portfolio/System landscape label | برچسب سبد؛ نه Capability منفرد |

طبقه‌بندی همیشه فقط یک برچسب ندارد. «افتتاح حساب غیرحضوری» از دید مشتری Business Service و از دید عملیات یک Process است. نکته این است که سطح مورد استفاده در Diagram صریح باشد.

## 8. نام‌گذاری Capability

نام خوب معمولاً از یک فعل/توانایی پایدار و یک موضوع کسب‌وکاری تشکیل می‌شود:

```text
Manage Customer Relationship
Manage Deposit Obligations
Assess Creditworthiness
Execute Payments
Control Financial Position
```

اما «مدیریت» را کورکورانه به همه‌چیز اضافه نکن. نام باید مرز معنا را روشن کند. «مدیریت امور بانکی» هیچ مرزی نمی‌دهد.

### نشانه‌های نام بد

- پسوند `System`، `Platform`، `Portal` یا نام Vendor
- نام جدول یا Entity فنی
- نام کانال مانند Mobile/Branch در L1
- عبارت بسیار ریز و عملیاتی مانند «چاپ رسید»
- عبارت بسیار کلان مانند «بانکداری»
- ترکیب چند توانایی با «و» بدون Outcome مشترک

## 9. Capability با Bounded Context یکی نیست

Capability از منظر Business Architecture توانایی سازمان را بیان می‌کند. Bounded Context از منظر مدل‌سازی، مرز اعتبار یک مدل و زبان را تعیین می‌کند. نگاشت آن‌ها ممکن است:

- یک Capability در چند Context پیاده شود.
- چند Capability در یک Context منسجم پیاده شوند.
- یک Context بخشی از یک Capability را برای چند کانال ارائه کند.

پس از Capability Map نمی‌توان مستقیم تعداد Microserviceها را شمرد.

## 10. مثال هدایت‌شده: «سامانهٔ تسهیلات»

عبارت Legacy را باز کن:

```text
سامانهٔ تسهیلات
├── طراحی محصول اعتباری
├── پذیرش و ارزیابی درخواست
├── تصویب و انعقاد قرارداد
├── اعطا و برنامهٔ بازپرداخت
├── محاسبهٔ مطالبات
├── وصول و پیگیری بدهی
└── تولید Fact مالی
```

این فهرست هنوز مرز نهایی نیست، اما نشان می‌دهد یک Application می‌تواند چند Capability و چند Subdomain را در خود فشرده کرده باشد. اسم Application نباید جای تحلیل را بگیرد.

برای `اعطای تسهیلات`:

- Capability: مدیریت تعهدات و پرداخت اعتباری
- Outcome: قرارداد مصوب به تعهد اجرایی و پرداخت قابل‌رهگیری تبدیل شود.
- Owner اولیه: کسب‌وکار اعتبارات/Lending
- KPI نمونه: زمان اعطا، نرخ خطای پرداخت، درصد اعطای تکراری صفر
- Process فعلی: ممکن است دستی، Workflow یا Event-driven باشد.
- Systems فعلی: ممکن است چند Legacy و Core را درگیر کند.

## 11. خطاهای رایج

### «هر چیزی که Business نام دارد Capability است»

خیر. Product، Process، Rule و Business Service هم Business هستند ولی نوعشان متفاوت است.

### «Capability را تیم مالک است، پس Team همان Capability است»

Owner و موضوع مالکیت یکی نیستند. ساختار تیم می‌تواند تغییر کند.

### «یک Capability یک API دارد»

یک Capability معمولاً با چند Use Case و Contract محقق می‌شود و یک API ممکن است بخشی از چند Capability را در یک Facade پنهان کند.

### «Capability Map همان Application Portfolio است»

Application Portfolio می‌گوید چه سیستم‌هایی داریم؛ Capability Map می‌گوید چه توانایی‌هایی لازم داریم. Overlay این دو برای کشف Duplicate و Gap مفید است، اما یکی نیستند.

## 12. تمرین هدایت‌شده

عبارت «کارمزد» را بررسی کن:

1. «محاسبهٔ کارمزد انتقال» احتمالاً Rule/Use Case است.
2. «سامانهٔ کارمزد» Application است.
3. «مدیریت قیمت‌گذاری و کارمزد» می‌تواند Capability باشد، اگر Outcome و Owner روشن داشته باشد.
4. `FeeCalculated` Event است.
5. «کارمزد پل» Product pricing term است.

همین واژه در پنج سطح ظاهر می‌شود. نام مشترک دلیل هم‌نوع‌بودن نیست.
